Result: partitioning alone (no index) is a real, substantial win --
mean=2.12s vs. the unpartitioned/unindexed baseline's mean=6.99s, a
~3.3x improvement -- because pruning to the January partition means
scanning ~3.48M rows instead of the full 11.2M. It's the second-best
single optimization tested here, beating the rejected single-column
index (6.74s) and nearly matching the composite index (1.74s).

This is what makes the 04_partitioned_explain.txt result (partition +
index together = 1.99s, no better than the index alone) make sense:
partitioning and the composite index are solving the *same* problem
for this query (skip non-matching rows via the leading
tpep_pickup_datetime predicate), so combining them doesn't compound.
In production, partitioning's independent value shows up on queries
that don't already have a covering index for the same predicate, or
at a scale where a single partition still exceeds the buffer pool.
